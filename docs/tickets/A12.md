# A12 — Stream, controls and clarification UX

Status: implemented and locally verified September 24, 2026, based on baseline
`a19f023` (A11). Prerequisites: A11, E07, E08, B12, D11, E10 and E11.
Implementation is recorded in the commit containing this handoff. No deployment
was performed and no model provider was called.

## Changed behavior

The Research view's run card now provides:

- **Streamed activity with a polling fallback** (`lib/run-feed.ts`).
  - The client opens `GET agent-runs/{r}/stream?after=<cursor>` with
    EventSource and merges each event by sequence. The server replays a
    bounded batch and closes.
  - The client reopens from its own cursor after 2 s (15 s in a hidden tab).
    It does not rely on `Last-Event-ID`, which Chrome did not send on
    intercepted reconnects and which a proxy could drop.
  - A replay that repeats earlier events never duplicates a row.
  - A connection that never opens, or a missing EventSource, switches to
    polling `/events` by cursor. That is A11's cadence: 3 s, 15 s hidden,
    backoff to 60 s.
  - While streaming, the run record is re-read 250 ms after events and at
    least every 15 s.
  - A finished run is read once and its remaining events are drained.
  - The card states which transport is in use.
- **Pause, Resume and Cancel.**
  - Each control posts the run's current `expected_run_revision` with a
    request key. The key is reused for the same run, control and revision, so
    retrying after a lost response cannot apply a control twice.
  - Pause appears for queued, running, waiting-for-job and waiting-for-input
    runs; Resume for paused runs; Cancel for any unfinished run.
  - Cancel needs a confirmation step that says committed effects are not
    rolled back.
  - The acknowledgment separates:
    - what was requested, and at which revision;
    - the recorded state (with its revision);
    - what that state means;
    - the server's `control_effect` statement;
    - this run's jobs still queued or running, for pause and cancel.
  - A 409 says nothing was applied and reloads the current state.
- **One clarification card.** All open questions for the run appear in one
  form. For each question it shows:
  - its prompt and the plan steps it blocks (by objective);
  - the number of cited sources;
  - the options with their consequences;
  - an "Another answer" choice, or a text answer when there are no options.

  The card also names the steps that are not blocked and can continue.
  - Drafts are kept in local storage for each question revision and survive
    a refresh.
  - Submitting sends every answer with the expected run and question
    revisions.
  - A stale or expired question (409) says nothing was applied, keeps the
    draft and reloads.
  - A successful answer clears the draft and reports the recorded state.
  - While questions are open, the card says Resume is not needed.
- **Plan revisions.** The current plan, plus earlier revisions under a
  disclosure (rationale and steps), noting that earlier results stay tied to
  their original plan.
- **Conditional specialist activity.** This section appears only when the run
  has assignments. Each shows its role, objective, plan revision, state and
  deadline, and findings are described as advisory.
- **Tool actions.** Action events name their tool (and attempt). A disclosure
  lists each action's state, job, output count, safe error code and whether
  it served a specialist. Tool arguments are not shown.
- **Partial and unsuccessful outcomes.** A partially completed run shows its
  stop reason as a first-class outcome, and its published results stay
  linked. Failed and cancelled runs show their stop reason too.

Hidden model reasoning is never requested or displayed. Only recorded
summaries, states and references appear.

## Interfaces and scope

`RunDetail` (`GET agent-runs/{r}`) gains three additive fields:
- `earlier_plans`: up to 20 earlier revisions, newest first.
- `actions` (`RunActionView`):
  - identity, tool, attempt and state;
  - specialist `assignment_id`;
  - `job_id` and output `artifact_ids`;
  - a safe `error_code`, only if it is a known code.

  Request arguments are never included.
- `assignments` (`RunAssignmentView`): role, objective, plan revision, state,
  creation time and deadline. There are no tool grants or budget allocation
  IDs.

The contract export count stays at 55: `run_detail`, catalog, response and
OpenAPI entries changed. There is no migration or environment change.
`Workbench` gains `refreshJobs()`, so an acknowledged control or answer re-reads
jobs immediately. A11's fixture was recaptured with the extended detail.

## Limits and downstream ownership

No browser-to-real-backend workflow, PostgreSQL acceptance, live provider,
hosted deployment or Linux startup was run for A12. `private-access` and
`workflow.spec` were not rerun.

- **Stream semantics.** The stream is bounded replay plus client reconnect,
  not a held-open push, so new events arrive within about 2 s.
- **Amendments.** Changing the goal, inputs or policy of a running run
  (`amend`) has no UI. A changed objective should be a new request or a
  continuation.
- **Specialist results.** Their findings are not exposed by any read route, so
  only assignment state is shown.
- **Answer keys.** A retained answer key lives in memory for this page. After
  a reload, a new key is used, but the expected question revision still
  prevents a double answer.
- **Downstream.** Browser-to-real-backend acceptance, hosted acceptance, two
  datasets/projects and private access remain A10.
