# B04 — Durable operation submission

Status: implemented; local Windows and Linux/PostgreSQL acceptance passed on September 19, 2026.

Prerequisites: [B03](B03.md) and [D03](D03.md). The [submission service contract](../submission.md) documents callers, identities, admission, transaction ownership and remaining boundaries.

## Changed behavior

- All queued HTTP operations, including original-PDF upload and attached-PDF ingestion, use `SubmissionService`. The service owns its transaction and commits before job serialization or tool return. The scientific worker remains the executor.
- Typed normalization and canonical payload identity are shared by UI routes and future internal tool dispatch. Exact replay returns the original job; changed content/kind/retry references conflict. Default expansion, object ordering, array ordering and the existing digest format are explicit.
- PostgreSQL project row locks serialize new submission admission. SQLite uses a no-op project write for its writer barrier. Existing unique constraints/savepoint arbitration remain the persistence backstop.
- Report-key replay precedes newer active-job checks. New reports still reject active project work. Changed evidence references conflict before new-input lookup; exact replay still checks current input scope.
- Trusted tool scopes require a run and explicit artifact/material allowlists. Run/action/attempt IDs derive a stable bounded request key in a reserved namespace. Replays cannot bypass scope; a benchmark also requires its consumed parent audit. Tool PDF ingestion requires a scoped material, never a bare storage digest.
- New Dataset 2.0 benchmarks require resolved source-card declarations before acceptance. Detailed upstream scientific validation stays in the worker. Retry references must name a compatible failed terminal job in the same project and preserve its canonical payload.
- Legacy PDF bytes publish outside the metadata transaction, with validation/replay checks before publication and locked rechecks afterward. A replay/conflict does not write bytes again.

No new migration, environment variable, dependency pin or HTTP schema is introduced by B04. B03 migration 0003 is still required. Existing B03 work was preserved.

## Handoff and limits

E03/B11 must construct scopes from persisted authorized records, enforce capability/policy/budgets and record the action-to-job association. B04 does not implement or enable an agent runtime. Agent failure recording and restricted reports explicitly reject until actor-aware failures and B06 scoped capture exist.

The project barrier coordinates submission admission, not a complete publication/report snapshot protocol. B05/B08 own complete lineage/publication, and B06 owns request-time report snapshots. B07/D04 own external-outcome reconciliation and automatic retry policy; B04 only validates explicitly supplied retry references. It does not make uncertain external imports safe to retry blindly. A09 owns broader browser request-key persistence/reconnect behavior.

No frontend code or generated contract output changed for B04; the earlier B03 frontend changes remain in the working tree. Not rerun: frontend build, browser end-to-end suite, hosted deployment, backup/restore or live provider evaluation. Lost-response acceptance was tested at the HTTP serialization boundary rather than by physically disconnecting a browser. Nothing was committed, pushed or deployed.
