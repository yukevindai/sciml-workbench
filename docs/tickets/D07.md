# D07 — Coordinated backup and restore

Status: implemented with isolated Linux/PostgreSQL restore acceptance. Production
Render capture/restore and release acceptance remain unverified; D06's recorded
private-access failure has not been cleared by this ticket.

`workbench.backup` provides offline `create`, `verify` and `restore` commands. It
captures the full PostgreSQL database (including durable checkpoints and every
ledger), complete file volume/upstream SQLite/provisioning state, application and
migration revisions, and a non-secret versioned configuration reference. The manifest
records file hashes and every user table's row count/content fingerprint plus
sequence values. Source-change detection, staged publication, filesystem syncing,
safe diagnostic output and new-target-only restoration make failures explicit.
Restore verifies all files before database IO, uses a single PostgreSQL transaction,
checks restored database contents and never starts application writers.

The backend image now supplies PostgreSQL 16 client binaries. CI installs the same
client major and opts into full-database restore tests with a disposable `CREATEDB`
account. `workbench.maintenance` gives Render a constant private health endpoint
while keeping the disk mounted without starting setup, API, scientific or agent
writers. The [operator procedure](../backup-restore.md) covers quiescence, secret
references, protected transfer, isolated restore, ownership, application validation,
leases, unknown usage, compatible upgrades and measured recovery time.

Acceptance uses real PostgreSQL dumps and PostgresSaver checkpoints, an installed
scientific audit/report and scientific replay, and the actual Failure Memory public
API. After restoring a report that was published before coordinator completion,
the run completes with no extra model call, job or artifact; a paused control stays
paused and budget/exposure records match. After restoring an import whose response
was lost after upstream commit, recovery resolves the same original external record
and repeated recovery publishes nothing further. No direct upstream-table edits or
paid provider calls occur.

Initial September 22, 2026 drill: **9 passed**, no skips. The synthetic report fixture
uses a three-row CSV and two projects. Database/file restoration measured **0.647 s**
for the report fixture and **0.815 s** for the import fixture; the complete report
seed/capture/restore/replay/resume drill took **5.824 s**. These are small local
fixture timings, not a production recovery SLA.

Final clean backend-image build and Linux/Python 3.12/PostgreSQL verification:
**22 passed, no skips** across backup/restore, maintenance and hosted supervision.
The image's own `pg_dump` and `pg_restore` report **16.15** and completed both drills.
Final restore measurements were **1.119 s** (report) and **0.579 s** (import), with
**6.566 s** for the report seed-through-resume drill. `pip check` and
`git diff --check` passed. These suites overlap the initial run. No hosted CI run
or real Render maintenance/recovery is claimed.

Limits: writer shutdown is an explicit operator precondition; the tool cannot fence
an unrelated live process. Checksums establish integrity, not backup authenticity.
No atomic transaction spans PostgreSQL and the filesystem; failures leave isolated
targets offline for investigation. Fresh secret/configuration provisioning and OS
ownership remain operator tasks. No production database, deployed service, provider
configuration, commit or push was changed by this implementation.
