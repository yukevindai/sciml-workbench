# A07 — Failure memory and receipts

Status: implemented and locally verified September 24, 2026, based on baseline
`b2ba979`. Prerequisites: A05, C06, B07 and D04. Implementation is recorded in
the commit containing this handoff. No deployment was performed.

## Changed behavior

- **Recorded failures** show who recorded each one and what was observed:
  - Human-assessed or recorded by an agent.
  - For agents: research run, action, assignment, provider/model, prompt
    version and policy rule.
  - For human Failure 2.0 records: the operator session reference.
  - The observation: an exact execution error with its code, a missed
    predeclared criterion (protocol, revision, metric pointer and partition,
    observed value, required comparison and threshold), or a researcher
    assessment.
  - Reason, uncertainty, unverified causal hypotheses, source job, a link to
    the exact benchmark run, and the Failure Memory record/project/import IDs.

  Failure 1.0 records are shown as legacy human assessments with no stored
  actor details, never as agent records. Their uncertainty comes from the
  upstream record, and reads "Not recorded" when absent. Records can be
  filtered (all / human / agent) and searched. Before A07 each record showed
  only its reason, date and raw JSON.
- The upstream record inside a Failure 1.0 artifact includes the run's metrics
  at import time, test scores included. Those values stay inside the collapsed
  complete-record JSON, which is labeled as containing them. The readable view
  does not repeat them. Listing records exposure as in A05.
- **Import receipts** lists every failure import from `job-index?kind=failure`,
  following pagination up to 1,000 jobs and warning if there are more. Each
  receipt state has a distinct label and explanation:
  - Prepared, not sent.
  - Outcome unknown: may or may not exist upstream; reconciliation required;
    a new assessment does not resolve it.
  - Confirmed.
  - Confirmed, not yet published.
  - No receipt recorded / not yet journaled.

  Each row shows the external ID, submission attempts, last admission time,
  upstream record, request digest and linked workbench record. A confirmed
  receipt on a job that failed (for example, recovered after a lost response)
  keeps the job shown as failed with its original error code, and says the
  later confirmation is recorded separately. Receipts reload when a failure
  job changes state or on **Refresh receipts**. Read failures are shown and
  can be retried.
- **Manual assessment** no longer silently selects the latest run: the
  researcher must choose one. Each draft (run, reason, uncertainty) gets one
  request key. A double click sends one request, and a retry after a failed or
  lost response reuses the key, so it resolves to the original job. Editing the
  draft starts a new key. The draft is kept on failure and cleared only after
  acceptance. The accepted job links to its receipt. While any import is
  unknown, the form warns that a new assessment is a separate record.
- `/failure-memory?project=<p>&failure=<id>#failure-<id>` focuses a record and
  `&benchmark=<id>#assess` preselects a run to assess. Unknown IDs show an error
  and substitute nothing. Failure jobs link to their record. Benchmark outcome
  history links to each record and to assessing that exact run.

## Interfaces and scope

There is no backend behavior, route, contract, migration, dependency or
environment change. A07 uses the existing `/failure` submission (request-key
idempotency), `job-index` receipt projections (B09) and D04 recovery. It adds a
generated `validateJobPage` decoder use (`parseJobPage`), `lib/failure.ts` and
`components/failure-inspection.tsx`. There is still no reconciliation or
recovery control in the UI: D04 recovers automatically, and operator
reconciliation stays a trusted backend interface.

- Two concurrent `/failure` posts with one key, plus a sequential repeat,

## Limits and downstream ownership

No browser-to-real-backend workflow, PostgreSQL acceptance, live provider,
hosted deployment or Linux startup was run for A07. `private-access` and
`workflow.spec` were not rerun. Request keys live in page state: a reload
followed by resubmitting the same text creates a new request. The job index
does not project which benchmark an unknown import targets, so the warning is
project-wide. Recovery history (`job_recoveries`) is not exposed over HTTP.
Failure 2.0 records are created by trusted/agent services, not by the manual
form, which still writes Failure 1.0. Provenance and report scope remain A08.
Job recovery UI remains A09.
