# B11 — Agent persistence and ledgers

Status: implemented; acceptance evidence recorded below. Scheduling and provider execution remain disabled pending D11/E04.

Alembic `0006` adds 16 application tables for trusted policies, conversation history, runs/revisions, assignments/actions, scoped job ownership, questions, usage, ordered events, protocol links and memory. Database constraints and retention triggers protect identity, scope, original intent and terminal state. LangGraph/PostgresSaver dependencies are pinned; `python -m workbench.checkpoints` performs supported, explicit, repeatable runtime setup.

The trusted run service persists intent before effects, rechecks current policy, fences stale prepared actions, binds accepted jobs transactionally, and reconciles exclusively from authoritative application records. See [persistence and control contracts](../agent-persistence.md) for APIs, migration/restore instructions and downstream boundaries.

Verification includes SQLite and PostgreSQL migration parity/roundtrips, populated scientific-data preservation, concurrent request/action/event constraints, actual graph checkpoint save/reload, and a PostgreSQL custom-format dump restored into a separate disposable database. The restore retained a run waiting on an accepted scientific job with an older checkpoint, an unanswered question, a paused run and an unresolved 512-token reservation. Application ledger contents and checkpoint contents matched the source; recovery found the original submitted action/job.

No application database was migrated. No provider call, deployment, commit or push was performed. E03/E05/E06/E08/E09 own full dispatch, accounting, specialist, recovery and memory behavior; D11/D12 own leased advancement and process/publication enforcement.

That assertion was updated and passes in the final focused suite. Ten browser contract tests, TypeScript typecheck, schema/generator drift checks and `pip check` passed.
