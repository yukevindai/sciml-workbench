# B07 — External operation journal

Implemented September 19, 2026 on baseline `2486a08` (B04 and C06 available). See the [journal and reconciliation contract](../external-operations.md).

## Changed behavior

- Alembic `0004` adds project destination bindings and an external-operation journal with same-project job/artifact references and database immutability guards. Existing records are preserved; no historical confirmation is inferred.
- Worker preparation freezes the original job-based external ID, connector, exact UTF-8 import body and both byte/request digests. The original request cannot change during recovery.
- Destination provisioning and import remain bounded subprocess operations. The parent persists destination and unknown submission outcome before import, then records a validated receipt before guarded artifact publication. Subprocesses receive no workbench database credentials.
- Lost responses and interrupted imports remain unknown, including a crash after upstream commit. Trusted reconciliation repeats the exact original import and resolves the same upstream record. Changed bodies/destinations and cross-project requests reject before import.
- Confirmed receipts retain their first snapshot. Artifact linkage is atomic with normal fenced publication. A failed original job stays failed even after receipt reconciliation; automatic recovery and missing-artifact publication remain D04.
- Explicit retry jobs cannot replace an existing journaled import identity. A new researcher assessment remains a new request. No public HTTP contract, dependency pin, UI or environment setting changed.

## Verification

- Windows/Python 3.12 journal suite: **13 passed, 13 skipped** (PostgreSQL counterparts run in Linux).
- Windows metadata, worker, real upstream workflow and C06 adapter regressions: **45 passed, 38 skipped**.
- Exact-byte response-loss test calls the real public upstream import, discards its committed response, and verifies reconciliation returns the same record. Tests inspect committed journal state, counters and unchanged failed-job history.
- Additional cases cover concurrent reconciliation, saved destination reuse, changed bodies, cross-project reads, receipt mismatch, atomic publication rollback/linkage, SQL identity mutation/deletion, populated downgrade refusal and real subprocess publication.
- Final Linux/Python 3.12.14/PostgreSQL 16 run: **126 passed, 6 skipped, 1 failed** across the journal, metadata, worker, workflow and split suites. All **26 journal cases** passed, including the PostgreSQL concurrency cases. Skips are SQLite parameters for PostgreSQL-only checks.
- All **39 schema/OpenAPI files** match in Windows and Linux; whitespace, Python compilation and Linux dependency consistency checks pass.

The initial Linux full run had **449 passed, 10 skipped**, one cluster-split exact-replay mismatch, and four repeated-trigger setup errors. The trigger installation was corrected and all four workflow setup cases passed in final verification. The unchanged `test_seeded_adapter_replay_and_full_public_diagnostics[cluster-extra5]` still fails its exact comparison of repeated upstream cluster diagnostics, including when run alone. No split code or test was modified; this remains a separate scientific regression. The full suite is therefore not claimed green.

## Handoff

Apply `0004` before starting updated workers. D04 owns automatic recovery eligibility, scheduling and guarded publication of a missing Failure artifact. B09 owns authenticated receipt projections; C07 owns Failure 2.0 assessment semantics. The internal reconciliation service requires an authorized project from its trusted caller and never queries upstream tables.

The standalone C06 live-search adapter still uses name markers; persisted B07 import destinations are independent of those markers after binding. Interrupted initial provisioning before the binding commit may still require operator inspection if the remote identity was independently renamed.

Verification used the disposable `sciml-b07-journal` Compose project; its containers, network and database volume were removed afterward. Included in the B07?B09 implementation commit. No application database or deployment was changed.
