# A01 — Research shell and typed fixtures

Status: implemented and locally verified on September 23, 2026, based on
baseline `0409fcc`. Implementation is recorded in the commit containing this
handoff. No deployment was performed.

## Changed behavior

- `/` and `/research` open a research entry with real project and dataset context,
  links to the manual tools, honest unresolved declaration display, and explicit
  notice that automated requests and controls are not available in this interface.
  All eight existing manual views retain their routes.
- The header shows labelled project and dataset selectors. Dataset choices are
  remembered per project across navigation and reload, checked against the loaded
  artifacts, and reset with dependent selections when the project changes.
- Initial workspace/project loading, empty workspaces, projects without datasets,
  response validation failures, and retry actions have distinct presentations.
  Failed polls retain the last validated data with a visible stale-data notice.
  Polling waits for each read to settle; sequence and project checks ignore late
  reads and reject foreign-project artifacts/jobs before display.
- Mobile navigation and the home link retain accessible names when text is
  hidden. The skip link targets a focusable main region. Existing focus treatment,
  theme tokens and reduced-motion support are preserved.
- Job activity and the header call queued/running jobs **active jobs**, rather
  than calling all queued jobs running. `app/lib/status.ts` provides an exhaustive,
  generated-type-checked vocabulary for scientific job and research run states.
  Partial completion, input waits, cancellation and failure remain distinct;
  status descriptions do not establish scientific validity.

## Development fixtures

Run `npm run dev` in `frontend`, then visit `/dev/research-shell` for a populated
preview or `/dev/research-shell?state=empty` for an empty preview. The preview:

- is guarded on the server by `NODE_ENV === 'development'` and returns 404 in
  production, including when query parameters are supplied;
- displays a persistent **Development-only fixture preview** warning;
- uses generated wire types and the same runtime response decoders as live data;
- makes no API calls, has disabled context selectors, and cannot submit work;
- displays all execution status examples as samples, never as live controls.

Navigation links explicitly leave the preview for the live workspace. No fixture
is used as an API-error fallback. Browser tests independently intercept HTTP
responses to exercise loading, retry and stale-response cases.

## Interfaces and configuration

No backend API, schema, migration, package dependency, credential, or deployment
configuration change. Existing B01 generated types and decoders remain unchanged.
`Workbench` accepts an optional typed fixture and preview content supplied only
by the development server route. The shell adds `research` to its typed view set.
The local storage addition is `sciml-dataset:<project-id>`; storage failure remains
nonfatal. Existing `sciml-project` selection is preserved.

## Handoff and limits

A02 owns attachment/project intake hardening. A03–A08 still own dataset/run
lineage, form and scientific result presentation within individual manual views;
this shell change does not claim those views' full acceptance. A09 owns durable
submission identity, recovery/backoff and scientific job controls. A11/A12 own
the actual goal composer, conversation, plan/activity, stream and run controls.
Research state examples are a shared display contract, not a live agent UI.

Not run: full real-backend scientific browser workflow, backend regression suite,
clean Linux/Node 22 CI, hosted acceptance, or live model/provider evaluation.
The focused shell tests use intercepted HTTP responses and do not establish
scientific execution or end-to-end research completion.
