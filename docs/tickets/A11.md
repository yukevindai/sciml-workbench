# A11 — Autopilot request workspace

Status: implemented and locally verified September 24, 2026, based on baseline
`d12ee97`. Prerequisites: A02, B12 and E04. Implementation is recorded in the
commit containing this handoff. No deployment was performed and no model
provider was called.

## Changed behavior

The Research view is now the request workspace. It keeps the project and
selected-dataset context and the links to the manual views, and adds:

- **Goal composer.** A research goal (up to 4,000 characters) and three
  example goals. An example only fills the text; nothing runs until
  **Run research**.
- **Attachments.** CSV and PDF files can be dropped on the composer or chosen
  with a keyboard-accessible file input. Each upload goes through the existing
  `research-materials` route with its own retained request key and no source
  declarations, so provenance stays unknown. Attaching never starts research or
  spends model budget. PDFs are checked for a header and a 10 MiB limit first.
- **Input scope.** Every attachment (a CSV together with its dataset
  artifact), and every dataset that has no attachment record, is listed with a
  checkbox. The active dataset starts selected until the researcher changes the
  selection. Each input is marked as authorized or not authorized by the saved
  policy.
- **Saved-policy summary.** One compact line shows the policy revision, model
  requests, tool calls, scientific attempts, active minutes and spend ceiling
  (or that none applies). **Policy details** lists:
  - the data offered to the model;
  - authorized input counts;
  - specialist allowance;
  - automatic failure recording, report verification and reuse;
  - whether the goal text is offered to the model;
  - the allowed tools and the policy reference.

  The workspace cannot edit policy.
- **Run research** sends one `POST agent-runs` with:
  - the trimmed goal;
  - the selected material and artifact IDs;
  - the stored project-policy revision;
  - the policy's limits;
  - `mode: autopilot`.

  Nothing else is posted: no plan approval or other confirmation follows.
  The button stays disabled, with the reasons listed, when:
  - there is no goal;
  - the policy is missing or still loading;
  - agents are unavailable (the server's configuration reason is shown);
  - a selected input is not authorized.
- **Optional Review plan.** A checkbox sends `mode: review_plan`. When such a
  run is waiting with its plan and no open question, the run card offers
  **Accept plan revision N**. It posts `review-plan` with the expected run and
  plan revisions and a request key that is kept while the page stays open.
- **Retained request key.** The run request's key and exact body are kept in
  local storage until the server accepts it or refuses it outright. The same
  rules as A09 apply: 4xx other than 408/429 is a definitive refusal. After a
  lost response, the workspace shows **Unconfirmed research request** with
  **Resend with the same key** and **Forget**. Running the same goal, inputs,
  mode and policy again reuses the key and returns the original run. Loading
  the page never resends.
- **Current run.** The run card reads the durable record: `GET agent-runs/{r}`,
  then `events?after=<cursor>` in pages of 200, merged by sequence. It shows:
  - the goal, state, mode, times, stop reason and continuation link;
  - the published plan (rationale and ordered steps with their status);
  - ordered activity: event type, recorded summary, time, action and
    artifact count;
  - result artifacts, linked to their inspector or to Provenance when the
    kind is not loaded yet;
  - the scientific jobs this run submitted (from A09 `run_links`), linked to
    their job-activity anchors;
  - usage against limits, cost (estimated or unknown with its reason) and
    the server's stop-control statement.

  No hidden reasoning is requested or shown. Unfinished runs are polled every
  3 s, or 15 s in a hidden tab, backing off to 60 s on failure while keeping
  the last read visible. Finished runs are read once.
- **Survives refresh.** Run history is read from the server: up to five pages
  of 100, sorted newest first here because the route pages by ID. The run
  shown is chosen in this order:
  1. the run this browser last selected;
  2. otherwise the newest unfinished run;
  3. otherwise the newest run.

  A reload, or another browser, returns to the same run without submitting
  anything. A picker lists earlier runs.

The development fixture preview does not call these APIs (a new
`Workbench.preview` flag). The A01 shell assertion changed from "no Run
research button" to "Run research is disabled" when no valid policy is read.

## Interfaces and scope

New read route `GET /api/v1/projects/{p}/execution-policy` →
`ExecutionPolicySummary`:
- `project_id`;
- `agent_available` and `unavailable_reason`, from the same admission check
  that run creation uses;
- `policy`: the current server/project intersection as `EffectivePolicy`, or
  `null`.

`EffectivePolicy` carries:
- the reference;
- the stored `project_policies` row revision, which run admission compares
  (not the payload's own revision);
- exposure and allowed tools;
- limits, spend ceiling and reuse/failure/report/message flags;
- the material and artifact grants that belong to that project.

Other projects' IDs and provider model identities are never returned. The
route uses the agent router's egress guard. There is no policy-write route.
Contract exports go from 54 to 55 files: a new record schema, plus catalog,
HTTP-response and OpenAPI entries. There is no migration or environment change.

## Limits and downstream ownership

No browser-to-real-backend workflow, PostgreSQL acceptance, live provider,
hosted deployment or Linux startup was run for A11. `private-access` and
`workflow.spec` were not rerun.

- **Operator provisioning.** New attachments are not authorized until an
  operator adds their IDs to both the server and the project policy (empty ID
  sets grant nothing). A one-request demonstration on fresh uploads therefore
  needs a policy-grant step first. Policy expansion remains E01/E03 work, and
  the UI marks such inputs rather than hiding them.
- **Conversations.** There are no conversation or message routes yet, so
  requests carry no `conversation_id` and past goals are not a threaded
  conversation. Each run's objective is its record.
- **Storage.** Retained run keys and the remembered run live in one browser's
  local storage, with one pending run request per project. A different
  request replaces the retained one after it resolves.
- **History.** Limited to the newest 500 runs.
- **Questions.** Shown read-only, with no answer form.
- **Owned by A12.** Streaming (SSE with polling fallback), pause/resume/cancel,
  answering clarification questions, amendments and plan-revision diffs.
  Hosted acceptance remains A10.
