# D03 — Scientific worker claims and deadlines

Status: implemented; Windows development and Linux/PostgreSQL acceptance passed on September 19, 2026.

Prerequisites: B02 and [D01](D01.md); this working tree also includes [D02](D02.md). Tested against baseline `36a68ba42f6d23cc00b5f55ed244b0164a33842b` with the existing uncommitted work preserved. No commit, push or deployment was made. See the [scientific worker runtime](../scientific-worker.md) for operator behavior and limits.

## Changed behavior

- Claims retain their original token and worker identity through execution and publication. `process_job` requires that complete claim instead of reconstructing authority from a job ID. Competing workers consume durable queued work through B02's PostgreSQL claim primitive.
- Input preparation copies accepted metadata in a short transaction. The scientific process executes adapters, reads/writes immutable blobs, assembles reports and calls Failure Memory without holding a workbench metadata connection or transaction.
- A private guardian watches the fixed remaining deadline and worker parent. Computation runs in a separate process group with bounded TERM/KILL cleanup. Graceful worker shutdown interrupts current computation and stops the claim loop; parent death also triggers guardian cleanup.
- Deadline allowance derives from the database deadline recorded at claim time, then uses monotonic waits. Current configuration, preparation overhead and process startup cannot renew it. SQLite development timestamps now retain milliseconds for the same deadline comparisons.
- Tasks receive detached inputs and limited settings, with no database/API/provider environment credentials or claim token. Failure Memory credentials go only to failure-import tasks. Results use strict private JSON with a 32 MiB limit; malformed results become safe operational failures.
- The parent validates result identity, locks and rechecks the original claim/deadline, then commits artifacts, provenance, result linkage and terminal state together. Late success is rejected and publication rollback exposes no result. Original-fence failure updates cannot overwrite another terminal outcome.
- Failure Memory's shared local OS file lock replaces the workbench PostgreSQL advisory transaction held across upstream calls. Per-attempt input/output/scratch directories are private and cleaned after handled completion or interruption.

## Consumer handoff and limits

No metadata migration, public schema change, new dependency or agent integration is required. API routes continue queueing accepted operations; the scientific worker remains independent of the future agent scheduler. Callers of the internal worker helper must pass the original `JobClaim`. Science receives a detached `Work` message and returns an artifact; only the parent publishes metadata.

B08 still owns the complete publication service and its cross-operation lock order; B05 owns full scoped lineage and B06 owns request-time report snapshots. D03's report metadata copy occurs during execution preparation and does not establish a request-time snapshot barrier. B07/D04 own external import journaling/reconciliation and policy-governed retries, D11 owns agent scheduling, and D12 owns run-level cancellation. In particular, an interrupted Failure Memory call may have committed upstream even when no workbench result was published.

Supported supervision is Linux/WSL; Windows is a development-test path. Process groups do not contain deliberately detached descendants or survive every host/kernel/guardian failure. Metadata/filesystem outages can delay failure recording or cleanup. Abrupt worker death may leave private workspaces and unreferenced immutable blobs; no garbage collection is implemented. Deployment sizing for the additional guardian process was not benchmarked.

Not rerun for D03: frontend build/browser end-to-end tests, complete application Compose startup, hosted deployment, backup/restore or live model evaluation. D01 retains the separate full-stack startup evidence. D03's disposable containers, network and PostgreSQL volume were removed after verification. Existing D01/D02 and documentation changes remain uncommitted.
