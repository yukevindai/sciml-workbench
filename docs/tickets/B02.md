# B02 — Metadata migrations and invariants

Status: implemented; local migration and PostgreSQL concurrency acceptance passed on September 19, 2026.

Implementation commit: `543de69b94dddf42e2b0823cd8439d1f1ac46d15`.

Prerequisite: [B01](B01.md). The [migration guide](../metadata-migrations.md) documents the interfaces, maintenance procedure, compatibility rules, and rollback limits.

## Changed behavior

- Alembic revision `0002` preserves project/artifact/job identities and exact stored artifact/request payload text while adding canonical request digests, claim tokens, worker identity, fixed execution deadlines, safe error codes, and retry references.
- Composite foreign keys enforce same-project results and retries. Existing project-wide request-key uniqueness applies across operation kinds. Artifact identity/project/kind must agree with its JSON payload.
- Database triggers reject accepted-request changes, published-artifact mutations, deadline/owner changes, decreasing fences, and terminal-outcome overwrites.
- Submission uses a canonical digest and savepoint to resolve racing identical requests to one durable job; incompatible requests conflict.
- Short claim transactions record database time, use PostgreSQL `SKIP LOCKED`, and sweep expired claims in bounded batches. The current worker carries its claim into conditional publication/error updates. Stale or expired publication rolls back pending artifacts and provenance.

No public HTTP schema, artifact schema, frontend interface, environment variable, or dependency pin changes. The existing job response omits internal claim metadata. The 38 B01 schema/OpenAPI files remain unchanged.

## Migration and configuration

Stop API submissions and old workers/children before applying `alembic -c backend/alembic.ini upgrade head`. This is a coordinated maintenance upgrade, not a rolling migration alongside unfenced workers.

Legacy queued jobs remain queued. Legacy running jobs become failed with `WORKER_INTERRUPTED`, retaining their immutable request and original start time; no deadline or worker identity is fabricated. Completed jobs retain their results. Invalid existing identity/project/result relationships abort migration for explicit repair. Empty databases support downgrade; populated job tables refuse an information-losing downgrade and require a coordinated backup restore or a forward migration.

Only isolated test databases were migrated during implementation. No existing application database, deployment, or remote branch was changed.

## Remaining boundaries and consumer handoff

The current scientific `execute()` still holds a database transaction and the child still publishes. D03/B08 must complete transaction-free computation, parent-authorized publication, monotonic subprocess waits, and their broader recovery tests. This ticket supplies and exercises the required metadata/conditional updates; it does not mark D03/B08 complete.

B05 still owns full nested JSON lineage validation at publication. B07 owns external receipt reconciliation. B11 owns agent persistence, and D12 owns cancellation ownership/process enforcement. These guarantees cannot be inferred from the new relational constraints alone.

B03 can consume the new metadata once D02 is accepted. D03 additionally needs D01, B11 needs E01, and C06 needs C01. Subsequent work follows the blueprint's full dependency table.
