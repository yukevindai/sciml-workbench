# B03 — Projects and automatic input intake

Status: implemented; local Windows and Linux/PostgreSQL acceptance passed on September 19, 2026.

Prerequisites: B02 and D02. [Intake API and compatibility](../intake.md) documents behavior and limitations; [migration instructions](../metadata-migrations.md) cover revision 0003.

## Changed behavior

- CSV/PDF research-material bindings preserve exact bytes, require project-scoped request keys, replay identical requests and conflict on changed payloads. CSV dataset and provenance publication is atomic with its binding. Identical bytes retain distinct artifact ownership across projects.
- Migration 0003 adds scoped dataset foreign keys, request-key uniqueness, media/digest constraints and immutable binding guards. Existing metadata is not rewritten. Populated downgrade refuses loss of attachment bindings.
- CSV checks consume rows incrementally within byte, row, column and parser-field bounds. Malformed inputs return safe typed errors without publishing metadata. Unknown declarations remain explicit Dataset 2.0 values; source-derived/inferred submissions are not accepted without a resolver.
- Original PDFs are preserved before extraction, downloadable through their scoped binding and included in reports. Explicit ingestion uses the existing bounded worker; a prefix check is not a successful parse. Malformed PDFs fail ingestion without losing the original.
- Storage readers, scientific execution, benchmark projection, report/replay and generated frontend validators support Dataset 2.0 alongside frozen legacy records. Unresolved source declarations permit inspection but block benchmark source-card admission. Legacy source-bearing uploads continue producing Dataset 1.0.
- The CSV form starts with unknown declarations, resets declarations on file changes and requires explicit selection of synthetic example metadata. Upload response retries reuse the same key within the open form.

## Handoff and limits

Deploy migration 0003 before this API/report worker revision. There are no new environment variables or dependency pins. The attachment API preserves unparsed PDFs; it does not promise OCR, extraction success or verified evidence. Intake does not establish a license or scientific independence. Source amendments remain new assertions/new attachments; originals are immutable.

B05 owns complete nested lineage validation, C05 evidence semantics, C08/C09 expanded archives, A02 broader metadata/attachment UX, and E03 agent-facing dispatch. The current form retains retry identity only while mounted; durable browser drafts are not implemented. The legacy project and CSV compatibility routes remain non-idempotent. Provider execution is unchanged.

Not run: complete live browser-to-backend workflow, hosted deployment, backup/restore or live provider evaluation. The focused browser test used API mocks; real scientific/backend paths were verified separately. Nothing was committed, pushed or deployed.
